# Pairing any skill with independent implementation verification

Read for single-skill, multi-skill or framework/contract application requests.
This module defines the standalone pairing workflow. It supplies no task service,
validation authority or target framework. Read the full applicable target contracts
and the series handoff module before actual task operations.

## 1. What the user is asking to install

Separate three outcomes:

| Outcome | Actual deliverable / proof |
|---|---|
| Define/install a skill | Canonical instruction file and required resources; source/package confirmation |
| Apply a skill to an app | Its applicable framework/contract implemented in actual project entry points, state and configuration |
| Verify application | Independent evidence that the delivered app satisfies each original applicable requirement |

A copied SKILL.md does not implement its framework. A README, helper or fixture
does not prove it is called. A definition-only confirmer cannot certify app wiring.

Resolve the current user-authorized operation, target app and exact target skills.
Do not automatically apply every visible skill or load an entire catalog. Use
canonical `.agents` sources where supported. An absent definition can use an
authorized original package for definition installation, not an invented contract.
Resolve only applicable required companions; optional unrelated skills are not
prerequisites. If the target is report-only, invoking it remains audit/report work
unless separate implementation scope is actually authorized.

For ordinary full application, default to one implementation/verification pair.
Use a staged series only when necessary for the target's source/bootstrap/runtime
boundaries, capability dependencies or safely manageable scope. No universal pair
count, fixed project, platform, language, storage layout or named task function.

## 2. Extract the acceptance standard before implementation

Read each entire canonical target and its applicable required references. Preserve
the user's approved scope, explicit exclusions, safety boundaries, validation policy,
mandatory installation steps and actual applicability gates.

Build one concise requirement-to-evidence matrix:

- Stable requirement ID and exact target/source binding.
- Fixed required outcome and original source meaning.
- Applicability: required, optional/out-of-scope, or factually not applicable.
- Delivery stage and owning primary/verifier, if staged.
- Known verification method or bounded pending-delivery discovery.
- Expected positive/negative outcome, evidence, and acceptance rule.
- Actual authorization/execution constraints, dependencies and blocked next action.

Cover every applicable obligation and every required conjunct, not just headings or
file counts. Do not promote illustrative examples into extra requirements or declare
missing functionality N/A because implementing it is difficult. Multiple skills may
share checks, but keep each target's coverage/binding and acceptance independently
visible. Conflicting mandatory contracts require scoped resolution before affected
work; silently choosing the easier rule is not compatibility.

Keep three distinct baselines:
1. **Obligations:** canonical contracts, original specification and approved criteria.
2. **Pre-install app:** relevant starting behavior/configuration and required baseline observations.
3. **Delivered app:** actual implementation/wiring and relevant tested inputs/environment.

Expected implementation changes do not invalidate the contract. Changes to the
contract or protected plan do not inherit old approval/acceptance. Evidence affected
by tested-input changes is renewed; unaffected evidence can be reused only when its
dependency binding supports reuse.

## 3. Primary: implement the actual application contract

The complete primary payload contains:

- Verified project and exact target identities/source manifest.
- Original approved requirements, exclusions and complete shared constraints.
- Existing project capabilities and actual integration boundaries discovered so far.
- Required deliverables, fixed falsifiable acceptance criteria and stage.
- Applicable validation/approval/repair/resource boundaries and escalation conditions.
- Concise delivered-input handoff and evidence location, using actual tracked paths.

Do not guess future command names, middleware, adapters or service credentials.
Mark unresolved implementation details as discovery work within authorized scope.
The installer chooses ordinary equivalent coding methods without a per-choice diary.

Implement every applicable obligation through actual app wiring, not orphan helpers.
Preserve existing behavior and target-required compatibility. Add required guards
and use only genuinely authorized checks under the host/target policy. Never impose
Failure Gate, a new database, a particular runtime or a router merely to orchestrate.
When such a contract actually governs, preserve all its applicable constraints.

Publish a compact handoff: real delivered snapshot and changed boundaries,
requirement-to-implementation mapping, configuration identity without secrets,
actual validation evidence, unresolved items and known limits. A handoff helps the
verifier discover delivery; it does not prove compliance.

## 4. Verifier: inspect, prove, repair, re-prove

Create a real dependent verifier with the full original obligation matrix and actual
primary binding, not a task title or "check the work" summary. Default verification
is read-only; include repair permission only when the user actually authorizes it.
If absent, plan/report an audit and request the smallest necessary repair scope.

The verifier must:
1. Establish real delivered-input readiness in its own environment; recheck complete
   primary/verifier executable payloads and canonical/source bindings.
2. Independently trace actual entry points, callers, middleware/adapters, state and
   configuration against the fixed requirements. Inspect the app, not merely notes.
3. Resolve methods marked pending against actual delivery. Preserve original
   criteria; use the permitted amendment/resolution route and complete readback
   for changed protected payloads. Installer output cannot define easier criteria.
4. Perform required safe authorized checks at the actual owning boundary. Use
   positive, negative, regression, lifecycle or concurrency cases where required;
   do not add unrelated checks or escalate validation for confidence.
5. List every material gap BEFORE editing. Distinguish missing/wrong implementation,
   missing proof, wrong provisional methods and unavailable external authority.
6. Under explicit repair scope, build/correct missing implementation and renew
   affected bindings/evidence. Do not repair correct expected rejection into zero,
   invent providers/approval, fix unrelated product bugs or silently change criteria.
7. Obtain fresh independent post-repair acceptance through an actual authorized
   fresh context or host review route; repair-author self-review is insufficient.
   Missing independence blocks acceptance, not permission to fabricate a reviewer.
8. Publish a requirement-level result: expected outcome, actual raw result,
   source/implementation/environment binding, evidence, satisfied/failed/blocked/
   justified-N/A status, and concrete next action.

Appropriate fixtures prove isolated behavior; installed wiring and actual runtime
claims need their own real evidence. Future runtime requirements do not block an
expressly inert source-stage task, but remain explicit gates for runtime successors.
A correct expected denial/nonzero/finding can satisfy that case; it cannot satisfy
an unmet implementation requirement to remove the blocker.

## 5. Native task creation and composition

Use the complete [handoff protocol](series-state-and-handoff.md), not guessed APIs.
Discover actual supported create/read/update, finalization, dependency, delivery
and review interfaces. Drafting and starting are separate authorizations.

Ordinary sequential pairing finalizes and fully reads back the committed primary
before creating/attaching the verifier. If an applicable companion requires a joint
batch, use that actual supported route with real alias/reference resolution; verify
joint commit, finalized full plans, actual dependencies and bindings before either
can be reported ready for execution. Do not claim a sequential creation history for
a batch or evade a required batch by separate writes. If the requirements conflict
or the host cannot satisfy the required route, surface the concrete batching decision
or capability blocker before creation.

Before each write, reconcile matching current/legacy tasks and partial/unknown
outcomes. A timeout is not rollback. Never manufacture IDs, blindly retry, duplicate
running work, reopen terminal records or hide unfinished pairs. Fully read back
persisted plans and actual dependencies; metadata, stable titles and native labels
are insufficient. Unknown authoritative outcomes stay unresolved.

Two tasks is the default application shape, not authority to drop a required
file-only definition confirmation, resource verifier or independent final review.
If composition requires an extra obligation, explain and obtain its authorized
batching/scope before creating it. Do not recursively create verifiers for verifiers.

Native dependency release may not transfer isolated branch changes. Require actual
canonical sources/delivered outputs accessible to the verifier and later tasks.
Do not auto-merge or run a doomed verifier to manufacture readiness.

## 6. Acceptance, progression and claims

Accept only the declared stage and current scope after all applicable criteria and
independent proof are satisfied. A failed/stale/blocked requirement remains open.
Administrative closure, native Done/Merged or a copied success label is not accepted
verification. Verified application of one target cannot hide another target's gap.

Retain the original and resolved matrices, actual task refs, evidence bindings,
dependency/delivery checks and material amendments in the established tracked
records; no per-coding-choice ledger or redundant second registry.

A single accepted pair finishes its scoped application. A staged series prepares
only its next eligible pair when authorized and delivered prerequisites are ready.
Automatic wake-up is optional separate work; without a verified route, resume on
invocation. Do not add scheduling, polling, hooks, activation, remote CI or deployment
to a framework installation by implication.

Report separately: skill definition availability, app implementation delivery,
independent acceptance, actual runtime readiness, native task state and hook status.
Use "fully applied and independently verified" only when every applicable target
obligation has current accepted proof. Otherwise report the supported partial result,
exact remaining requirement, responsible role and next authorized action.
