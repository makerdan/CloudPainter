# Apply a skill and check the result

Read for applying one or more canonical skills to an app. This reference provides
the standalone pairing process, not a task service, approval system or target framework.
Read the complete applicable targets and handoff reference before actual task work.

## 1. Identify the requested result

| Result | Required deliverable |
|---|---|
| Define/install instructions | Canonical definition/resources and required package confirmation. |
| Apply instructions to an app | Actual entry-point, state and configuration integration. |
| Verify the application | Independent proof against every applicable original requirement. |

A copied file, README, orphan helper or fixture does not prove installed behavior.
A file-only confirmer cannot certify app wiring.
Resolve the actual authorized operation/project/targets. Do not apply every visible
skill or load a whole catalog. Use exact canonical `.agents` sources.
An authorized original package can support new definition installation, not an
invented contract. Resolve applicable required companions only; optional unrelated
skills are not prerequisites. A report-only skill remains report work without
separate implementation permission.

Default ordinary application to one pair. Stage only for real scope, dependency,
source/bootstrap/runtime or safe-size boundaries. No fixed project/platform/language/
store/task API/pair count.

## 2. Define success before writing code

Read entire canonical targets/applicable references. Preserve approved scope,
exclusions, safety, validation, mandatory steps and applicability.
The agent makes one concise requirement-to-evidence matrix:

- Stable requirement ID and exact target/source binding.
- Fixed original required outcome.
- Required, optional/out-of-scope or factually not-applicable status.
- Delivery stage and actual implementation/review responsibility.
- Known method or bounded permitted discovery against actual delivery.
- Expected positive/negative result, evidence and task acceptance rule.
- Real execution permission/limits, dependency and smallest missing next step.

Cover every required conjunct, not just headings/file counts. Examples are not extra
requirements; difficulty is not N/A. Shared checks retain each target's independent
coverage/binding. Resolve conflicting contracts through actual authorized scope;
do not silently choose the easier one.

Keep original obligations, starting-app observations and delivered-app evidence
distinct. Normal code changes do not change requirements. Changed protected plans/
contracts do not inherit prior approval. Renew affected evidence; reuse unaffected
evidence only with actual dependency support.

## 3. The implementation task finishes its part

Full task plan: verified project/target/source identities, complete original/shared
requirements/exclusions, discovered host integration boundaries, finished deliverables,
fixed acceptance criteria/stage, validation/repair/approval/limits/escalation rules
and actual tracked handoff destination.

Mark unknown implementation details as permitted discovery, not guessed commands,
middleware, adapters or credentials. Choose equivalent routine methods without diaries.
Wire applicable obligations into the app, not orphan helpers. Preserve compatibility,
existing behavior and required regression protections. Use only allowed checks.
No added Failure Gate/database/runtime/router merely to create a pair.

Publish a compact real delivered snapshot, changed boundaries, requirement mapping,
secret-safe configuration identity, actual checks and unresolved limits.
The implementation task owns technical preparation and record retrieval.
A handoff helps review; it is not self-issued compliance.

## 4. The verification task finishes the check

Create an actual dependent verifier with full original matrix/primary binding,
not a "check the work" title. Default audit is read-only.
Include genuine repair approval; if absent, request only the smallest needed scope.

The verifier must:

1. Establish accessible delivered inputs in its own environment; re-read full plans,
   canonical sources and bindings.
2. Trace actual entry points, callers, adapters, state and configuration.
3. Resolve pending methods within permitted scope. Fixed/protected changes need their
   actual amendment route/full readback; delivery cannot define easier criteria.
4. Run applicable safe approved positive/negative/regression/lifecycle/concurrency
   checks at owning boundaries, without unrelated checks or validation escalation.
5. Publish material gaps before repair, distinguishing wrong/missing implementation,
   missing proof, unsuitable methods and inaccessible/missing actual authority.
6. Repair only explicit scope, renew affected evidence/bindings, preserve correct
   expected refusal and unrelated behavior. Never invent providers or approval.
7. Arrange fresh independent post-repair acceptance through an actual authorized
   separate context or host review. A repair author's own claim is insufficient.
   Missing review access blocks that claim, not permission to fabricate a reviewer.
8. Record expected/actual outcomes, real evidence and satisfied/failed/blocked/
   justified-N/A requirements with concrete responsible next steps.

The review result and final accepted snapshot belong in the handoff, not a request
for owner receipts. A new task is not automatically needed for another review.
If extra tasks are genuinely required, explain and obtain actual scope before creation;
do not recursively create reviewers for reviewers.

Fixtures prove isolated behavior. Runtime/install claims need real host evidence.
Future runtime proof does not block an expressly source-only task's own completion.
Carry it to an explicit later task/gate. A correct denial/finding may satisfy its
approved case but cannot implement a missing capability.

## 5. Create tasks and pass files through supported routes

Use the complete [handoff protocol](series-state-and-handoff.md).
Discover actual create/read/update, finalization, dependency/delivery and review
interfaces. Drafting is not permission to start.

Sequential pairing fully finalizes/reads the primary before verifier attachment.
A governing joint batch uses real alias/reference resolution and commit/readback.
Verify finalized full records/real dependencies before reporting readiness.
Surface real conflicts or host limitations before writes; no guessed interfaces,
fabricated ordering or evasion of required batch semantics.

Reconcile current/legacy duplicates and partial/unknown writes before each create.
Timeout is not rollback. Never invent IDs, blindly retry, duplicate running work,
reopen terminal records or hide unfinished pairs. Full plans/dependencies matter;
metadata/titles/status alone do not establish handoff.

Two tasks is the default, not permission to omit genuine definition/resource/app/
final-review obligations. Explain actual extra scope/batching before creation.
Do not require a third native task when a supported authorized review context suffices.
Dependency release may not transfer files; verify accessible actual outputs.
Do not auto-merge or run a doomed verifier to claim readiness.

## 6. Finish only the approved scope

Accept current declared-stage work only after all applicable criteria and separate
proof. Failed/stale/missing requirements remain open. Administrative closure or
Done/Merged cannot substitute for accepted review; one target's success cannot hide
another target's gap.

Maintain original/resolved matrices, actual refs, evidence/delivery bindings and
material amendments in existing tracked records, not duplicate registries or method
ledgers. Finish all feasible in-scope work while one requirement is blocked.
After one accepted pair, its scoped application is finished. A staged series prepares
only the next eligible authorized pair. Automatic wake-up is separate optional work.
Do not add polling/hooks/activation/CI/deployment by implication.

Report instructions delivered, app work delivered, separate review, real readiness,
native lifecycle and optional hook state separately.
"Fully applied and independently verified" needs every applicable original outcome.
Otherwise name the supported partial result, exact missing requirement and next action.
The user does not reconstruct evidence, inspect version fingerprints or issue review
results. Preserve approval and truthfulness while keeping the task responsible.
