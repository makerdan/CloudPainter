# Keep the right tasks, records and delivered work together

Read fully for initialization, creation, resume or advancement.
These are required meanings/outcomes, not supplied runtime services.
All technical bookkeeping here belongs to the agent/workflow.

## 1. Bind the actual request

Record stable project identity, exact specification/version/digest, canonical source
closure, actual user planning/drafting instruction and scope.
Pin immutable contents or verified immutable references, not a mutable path alone.
Future draft permission does not approve tasks/tests/repairs outside scope, new
infrastructure, recurring scheduling or changed policy.

Reconcile changes to pieces, contracts, checks/repair, approval modes or specification
through their real renewed scope. Do not silently rebase on a new attachment or
self-modified backlog. Unspecified equivalent methods need no per-choice approval/
ledger. Protected plans/fixed criteria/material safety/scope/limits changes keep
their amendment/readback route. Relevant changed inputs invalidate affected evidence.
Missing future definitions can use only the authorized original-package exception;
dependent checks remain pending until actual canonical files exist.

## 2. Maintain durable progress without another approval registry

Reuse host equivalents. Optional record shape:

```text
series:
  schemaVersion, verifiedProjectIdentity, seriesIdentity
  specificationReference + version + digest
  canonicalSourceManifestReference
  preparationAuthorizationReference + scope
  orchestrationRevision + lifecycle
  currentPieceKey
  lastAcceptedPieceKey + acceptanceReference
  backlogReference + orderedPieceKeys
  checkpointLocation + writer/coordination mapping
  hookCapabilityReference + enabledState
  unresolvedWrites/conflicts
piece:
  pieceKey + generation
  declaredDeliveryStage + prerequisiteEvidence
  expectedOutcomeContract + requiredEvidence + taskAcceptanceMapping
  primaryReference + finalizedPlanRevision/digest
  verifierReference + finalizedPayloadRevision/digest
  primaryCreationBinding + verifierDuplicateBinding
  actualDependency + verifiedDeliveryReadiness
  testedImplementation/contract/environment bindings
  acceptanceReportReference + assessment
  pendingRepair + retainedIncidents
  nextAction + responsibleRole
```

Equivalent records can satisfy these bindings without literal names/schema.
No extra acceptance gate or prescribed architecture is implied.
Backlog/checkpoint locates work; original/native/local task, approval, allocation,
run and evidence records remain authoritative.
ResponsibleRole must identify the actual task/agent/provider and action, not become
"the owner must supply technical evidence." Never require original receipts.

Tracked plans, checkpoints, reports and canonical sources stay outside `.local`.
Only a genuinely required temporary submission copy is allowed: complete tracked
plan read first, full copy comparison, independent full persisted readback afterward,
no initial drafting/sole copy/runtime evidence, and ordinary readiness/approval gates.
Missing originals/readback block the affected handoff, not all independent work.

A tracked checkpoint may support serialized invocation-driven planning with actual
atomic writes/interruption handling. It does not coordinate independent clones,
branches or callbacks. Concurrent automatic preparation needs real shared CAS/
idempotency/exclusion; no branch-local lock or JSON read-modify-write is global.
Do not merge live database binaries as authoritative state.
Record genuine safe store/access/persistence mappings; exclude secrets/private context.

## 3. State means progress, not a verdict from one error code

| State | Meaning |
|---|---|
| UNBOUND | Project/request unresolved; no creation. |
| BACKLOG_READY | Complete scoped plans exist; earliest eligible pair can be prepared. |
| PAIR_PREPARING | One preparation intent is running; exclude competitors. |
| PAIR_INCOMPLETE | A write/link/readback is missing; finish this pair. |
| AWAITING_USER | Correct drafts await a specific user approval. |
| IN_PROGRESS | Authorized work is running; no duplicate/advance. |
| AWAITING_DELIVERY | Work exists but accessible inputs are not proved. |
| VERIFYING | The actual verifier is running; no replacement. |
| BLOCKED | Required permission/capability/evidence is genuinely missing. |
| RECONCILIATION_REQUIRED | Resolve changed records, duplicates or unknown writes. |
| ACCEPTED | Current declared-stage work has independent accepted evidence. |
| PAUSED | No successor drafting. |
| FINISHED | All applicable pieces accepted; no extra work implied. |

These meanings are not API names or native status writes. Do not simulate transitions
by changing task status. Expected BLOCKED/BLOCKING/nonzero/negative findings may
satisfy a task whose original criteria allow them and whose evidence/other criteria
pass. A native label alone does not settle the task.
For implementation, merely describing a missing feature does not build it unless
the approved specification explicitly accepts that finding/follow-up outcome.

Unmet verification stays current. Use the actual authorized retry/replan route, not
blind reopening/cancellation. Preserve identities/history and real generations.
Owner closure/waiver/cancellation/reduced scope does not pass the original series.
Record administrative outcome and obtain actual changed-scope permission before
successor preparation. Show users plain-language state, not unexplained enum labels.

## 4. Create/reuse the exact primary and verifier

Read applicable canonical targets and any actually governing compatible router.
No specific task function/platform/pair count is assumed.
Pin original scope/contracts and starting/delivered baselines.
Build complete plans with fixed outcomes, entire matrix, safety/repair permission,
actual report destination, dependency and bounded discovery/resume rules.
Do not guess future paths/digests.

Versioned primary creation binding: actual project, specification, piece, primary
scope/draft-plan digest and generation. Search real tasks before creation;
title-only matching is not duplicate proof. Ambiguity blocks another write.

Per-target verifier duplicate binding:

```text
[Project identity, exact target skill ID, primary namespace/ID,
 finalized primary-plan digest, canonical verification scope]
```

Persist encoding/version and full components, not just a hash. Preserve meaningful
case/bytes. Normalize truly equivalent unordered sets through a documented mapping.
Hash actual finalized representation, not status or reformatted copies.
Shared multi-target verifiers keep each binding and full independent matrix.
Series/piece/generation supplement this key; they do not replace it.
Source availability, manifests and snapshots are checked separately.
Do not silently change a stable key because source files changed.
Search applicable legacy/normalized bindings. Material changed plan/scope needs actual
renewal/linked history; unchanged obligations retain the key with resolved matrix/
executable revision recorded separately.

Normal sequential creation needs confirmed committed primary finalization and full
authoritative readback before attachment. Active writers, draft titles, repeated
unchanged reads and waiting do not prove finalization.
Read exact primary revision before/after linkage and at execution/acceptance.
Use real version preconditions; otherwise report bracketing/race limits.
Read entire verifier at create/reuse, execution and acceptance.
Missing/truncated/changed content blocks affected claims. Resolve permissible
mechanical differences within scope; real protected changes need an exact proposal.
The user should not manually compare digests or reconcile bookkeeping.

A mandatory joint batch uses real alias/commit/readback and finalized dependencies
instead; do not invent ordering/atomicity. Interfaces must preserve full plans and
actual dependency references. Prefer genuine atomic idempotency. Otherwise use a
supported coordinator, authoritative search/readback and truthful race limits.
Do not promise global exactly-once writes without proof.

Respect required definition confirmation and separate resource/app review.
Explain actual extra scope/batching before creating it; a two-card preference does
not authorize removing a contract requirement. A supported independent review
context is not automatically an extra native task.

## 5. Deliver files and the review decision

Re-read full executable plans/revisions at creation, reuse, execution, acceptance
and next-pair preparation. Metadata hashes, titles, dependencies and terminal labels
are not substitutes.
Resolve pending methods against delivered files/wiring without redefining outcomes.
Correct provisional methods only through actual permitted resolution/amendment.
Keep original/resolved matrices, reason/authority and evidence impact.
If no allowed route exists, propose the correction and block affected execution.
Protected payloads must be rebound/read before use.

Determine actual dependency release semantics. Isolated copies may not contain
merged work. Check accepted snapshot/reference access and readiness in the next
environment. Do not auto-merge to manufacture delivery or assume a task starting
means all required evidence transferred.

Acceptance covers every applicable original declared-stage requirement, tested
implementation/config/environment, raw expected/actual results and final separate
review after repairs. Missing evidence blocks dependent claims only.
Preserve expected negative/nonzero results; do not repair correct refusal into zero
or redefine criteria after unexpected failure. Finding tasks can finish while exposing
a genuine later prerequisite.

Do not demand future runtime proof for source-only tasks. Do not use source-only
acceptance as runtime proof. Assign deferred work to explicit later tasks/gates.

Use a real authorized fresh verifier/subagent context or host review.
The review route records its actual decision, criteria and final accepted snapshot;
the handoff retrieves it and makes it accessible to the next task.
Supported equivalent host records suffice; no redundant receipt ceremony.
Repair-author assertions are not separate review. Missing independence stays blocked.
Do not ask the user to supply review receipts or repeat acceptance.
Explain inaccessible records separately from a failed review.
New verification cannot recreate old approval, consumed budgets or unknown ownership.

## 6. Recover this work rather than create another copy

Classify writes as not committed, confirmed committed or unknown.
Timeout is not rollback. Reconcile primary/verifier/checkpoint through actual request
identity/idempotency or uniquely verified authoritative bindings before retry.
After primary creation, recover its real reference and finish verifier attachment.
After verifier creation, recover the actual pair and checkpoint.
Ambiguous matches/inaccessible authoritative lookup block another create.

Age/heartbeat/retained lock/missing callback does not prove work stopped.
Use target-specific bounded recovery, not unlinking exclusion or refilling allowance.
Finite reads/reconciliation must lead to a concrete next step, not endless polling.
Callbacks/new sessions/invocations cannot refill validation/diagnostic budgets.
Finish other independent permitted work. When only access/approval can unblock the
remaining item, give the exact limitation and smallest meaningful owner decision.
