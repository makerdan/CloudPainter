# Explain the work without making the user do it

Read when writing task briefs, approval questions, waiting messages or completion
reports. Use high-school-level English without assuming programming knowledge.
These rules clarify responsibility; they do not remove safety checks or grant approval.

## 1. Write a task that can finish

Every task brief must say:

- The finished result and its explicit boundary.
- Work the agent must do to reach it.
- Checks/evidence the workflow must obtain at this stage.
- Real inputs/dependencies, access and approved actions/limits.
- What is outside the task and what specific change needs user permission.
- Where the handoff/result will be recorded and how the next task gets it.

Use this human-facing shape, followed by required full technical plan details:

```text
Goal: [specific finished result]
This task handles: [in-scope implementation, records, checks and review]
Done when: [fixed original criteria and stage-appropriate evidence]
Needs first: [actual inputs/permission; agent retrieves them where possible]
Not included: [explicit exclusions]
Ask the user only if: [specific material decision/access/permission]
Result goes to: [actual supported tracked destination/next task]
```

Do not create title-only tasks or assume brackets are real IDs, commands or providers.
Fill them using actual discovery before task creation.

## 2. Keep these duties with the workflow

Find approvals/review records; choose permitted technical methods/tests; propose
safe time/attempt/resource settings; read original consumption; maintain IDs/versions/
digests; resolve duplicates/mechanical differences; deliver files; track progress;
arrange authorized separate review; fix in-scope defects; stop only approved owned
processes; recover interrupted work through real routes.

The user provides meaningful choices and permission, not records or system design.
Assume original receipts cannot be supplied. Never ask for them.
If access genuinely requires the owner's action, name that account action, not
"provide evidence." Credentials use the host's secure flow, never chat.

Do not override historical permission, unknown cleanup or consumed allowance by
running fresh checks. Missing review evidence may need a supported new review;
that still requires scope/access and cannot invent a past accepting decision.

## 3. Classify a block before asking anything

| Problem | Agent responsibility |
|---|---|
| Missing files/software | Retrieve/build within scope or propose the exact allowed integration. |
| Inaccessible records | Search real routes; name unavailable interface and supported remedy. |
| Missing approval | Check existing scope first; prepare the precise new decision. |
| Exhausted allowance | Read original usage; stop dependent launches; no automatic reset. |
| Failed check | Diagnose/fix within scope and renew required evidence. |
| Unknown running work | Retain exclusion; use approved exact cleanup/recovery. |
| Unavailable separate review | Propose/use actual authorized review route, not self-certification. |

Continue unrelated permitted work. Never call an expected safety refusal a defect
or a later runtime requirement a failure of an earlier source-only task.
Do not ask again for a resolved issue because it remains in a historical appendix.

## 4. Start with the useful answer

```text
Finished: [what is actually complete and whether tested]
Still needed: [one precise remaining requirement, or none]
Handled by: [actual task/agent/provider, not a vague owner role]
Next: [specific permitted action]
Your decision: [specific choice and consequence, or "None right now"]
```

Use only fields that add information; do not turn every update into a form.
Put raw codes, task/run IDs, hashes and exact versions in concise technical evidence,
not unexplained requests. Retain required precision behind plain-language explanation.

Illustrative examples, not claims about a current project:

- "The setup files are written. They have not been run or tested."
- "The safety check passed: the system refused an unapproved action."
- "The task has merged. I still need to retrieve its separate review result."
- "I cannot access that review record. This does not establish that the review failed."
- "The approved test allowance is used up. I will not start more tests or reset it."
- "A prior test may still be running. I will not start another until its state is resolved."
- "The wording disagreement was already resolved. No new decision is needed."
- "Closed because you requested it. This does not mean checks passed; unfinished work remains."
- "This part is accepted. The next part still needs its own permitted setup actions."
- "Say 'Prepare the next pair' to create the next drafts. That does not approve or start them."

## 5. Ask for a decision, not technical homework

Bad: "Owners must supply containment, accounting and an acceptance receipt."
Better: "I will retrieve the review and usage records and prepare the safe test
integration. Before any tests start, I will show you the exact actions and limits
that need your approval."
Only promise actions that available access and scope actually support.

Approval questions state the action, affected work, practical effect/risk/cost,
limits, exclusions and a concrete recommended choice when justified.
Do not ask users to select milliseconds, compute fingerprints, identify processes,
find reviewers or attest an installation themselves.
Routine already-authorized work needs no new human approval.
Material changes still do. Unsupported capabilities remain unsupported.
