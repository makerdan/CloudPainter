# Check the definition and the actual workflow separately

These are required checks, not claims that installation or tests passed.
Use actual source/plan/environment and safe applicable authority.
Do not perform platform writes merely to check instruction text.
Authoring-only changes do not imply confirmation tasks or execution.

## 1. Preserve original outcomes, not a coding diary

Implementation finishes the approved result; verification checks that result against
original criteria/evidence. Routine equivalent methods need no per-choice approval,
method ledger or narrated programming diary.
Actual fixed/protected changes, waivers, changed coverage/criteria or material scope/
authority/execution/limits/safety/privacy/compatibility/data-integrity/ownership/
recovery/completion changes retain their real amendment/full-readback requirements.
Required approval/execution/incident/provenance/review evidence remains necessary.
Tables specify outcomes, not mandatory internal methods or extra example-based gates.

## 2. Confirm an installed definition/package

When installation through project tasks requires dependent definition confirmation,
use actual supported host interfaces and applicable canonical companions.
SKILL.md-only confirmation/repair stays in that file; check required resources
separately. Definition confirmation does not enable a hook or apply a framework.
Compare actual files with the complete authorized original specification.

Check that:

- Identity remains `paired-task-orchestration`, meaningful triggers and entry point
  below 500 lines.
- The package is portable: no mandatory router, Failure Gate, task API, backlog,
  stack or fixed pair count.
- Definition delivery, actual app implementation, independent review and runtime
  readiness remain separate. Real entry-point/state/config proof is required.
- Complete per-target requirements, applicability, fixed expected positive/negative
  outcomes, shared coverage/conflicts and original/delivered bindings are retained.
- All canonical relative links resolve; complete source/resources are supplied.
- Original specification is pinned and real project/namespace/task references are used.
- Full finalized primary/verifier plans, dependencies, delivery and original/resolved
  matrices survive handoff. Titles/status/metadata alone are insufficient.
- Sequential creation or required joint-batch alias/commit/readback is real, not guessed.
- Stable duplicates/unknown writes are reconciled before retry; current pairs are reused.
- Default one-pair window respects actual approved exceptions and leaves unrelated
  historical cards alone.
- Audit precedes authorized repair, changed evidence is invalidated and fresh separate
  post-repair acceptance is obtained.
- Source/bootstrap/runtime stages do not require future proof too early or claim
  operational readiness from authored files.
- User approval stays separate from drafting; no silent tests/activation/CI/recovery/
  disruption/merge/deploy/recurring work.
- Actual required extra confirmation/resource/app obligations are explained before
  creation, not hidden or recursively expanded.
- Advancement needs current review and accessible files. Expected negatives may pass
  their original cases; unmet obligations and administrative closure do not pass.
- Authoritative deliverables/progress stay outside `.local`; its exception only allows
  required disposable copies after tracked original readback/full comparison and
  independent full persisted readback. No initial drafts/sole copies/runtime evidence.
- Optional hooks need actual events AND wake-up/task/coordination routes, separate
  approval and real proof. Fixtures/flags/unsupported APIs cannot supply them.
- Manual resumption works without an automatic route; polling remains optional
  separately approved recurring work.
- Reports require plain English, distinguish approval/capability/access/usage gaps,
  name the actual responsible task/agent and never require original owner receipts.

Publish gaps before authorized correction. Preserve unrelated canonical skills and
original obligations. Separate author readback from actual independent acceptance.
Do not quietly adopt new requirements into existing protected task plans.

## 3. Check actual host behavior

Use safely authorized native operations and real returned records.
Fixtures can test logic, not real task UI/integration.

| Case | Required result/evidence |
|---|---|
| Single target | Full canonical extraction, real app wiring and each applicable outcome proved. |
| Multiple targets | Each keeps independent coverage/binding; shared checks hide no gap. |
| Missing framework | Copied definition/README/helper cannot pass application/runtime requirements. |
| No router/Gate | Standalone pairing works without imposing either. |
| Joint batch | Real aliases/full committed records/dependencies read before execution. |
| First pair | Complete drafts within actual approval/window, real references and full finalized readback. |
| Existing pair | Reuse correctly bound work; no duplicate primary/verifier. |
| Future parts | Durable backlog; no unauthorized extra draft cards. |
| Approval | Creation alone starts neither task; covered existing approvals are reused. |
| Delivery | Missing isolated files block dependent execution; no auto-merge. |
| Shared instructions | Every full plan retains all applicable safeguards/expected outcomes. |
| Routine methods | Equivalent unspecified methods need no new approval/ledger; outcomes still pass review. |
| Temporary copies | Actual required path, tracked original read first, full comparison and persisted readback. |
| Local-only drafts | Lack of another writable path is not enough; no sole `.local` deliverables. |
| Protected changes | Real amendments, full readback and affected-evidence renewal. |
| Source stage | Accept only its scope; retain later runtime gates. |
| Missing implementation | List gaps, repair within scope and obtain fresh separate final review. |
| Missing authority | Exact proposal, not fake approval/provider or owner technical homework. |
| Wrong/stale plan | Full mismatch blocks affected creation/execution/advance claims. |
| Done without review evidence | No advancement claim from status alone; retrieve actual host review record. |
| Failed/stale/cancelled work | Unmet requirement stays current, not inferred solely from status. |
| Expected nonzero/negative | Satisfy only its evidenced original criterion with all other requirements met. |
| Correct refusal | Keep raw denial and explain successful safety behavior; do not repair it into zero. |
| Finding exposes future gap | Finding task may finish; later actual prerequisite remains open. |
| Owner closure | Administrative closure is not verified delivery. |
| Genuine extra task | Explain before authorized creation; no omitted requirement/endless reviewers. |
| Unknown writes | Recover actual partial pair through trusted bindings, not blind retry. |
| Concurrent resume | Actual coordination/idempotency establishes exclusion; otherwise report limitation. |
| Final pair | Finish without extra pair, auto-close policy, merge/deploy or recurring work. |
| No hook | Bounded manual resume remains available and clearly explained. |
| Missing receipts | Agent searches available records; never asks user for originals or assumes success. |
| Task ownership | In-scope gaps/records/reviews handled by the task; only necessary decisions reach user. |
| Existing decisions | Resolved issues are not repeated from historical reports. |
| Inaccessible evidence | Distinguish "cannot retrieve" from "failed" or "never happened." |

Automatic mode must also satisfy the complete real-host matrix in
[the optional hook contract](host-hook-contract.md). Do not call it verified from
source text, this table or simulated events.

## 4. Report actual completion and remaining work

The technical record contains original request/contracts, package manifest, actual
project/tasks, exact scope/stage, checks, raw outcomes, tested snapshot/environment,
gaps before repair, amendments, final separate accepted snapshot, unperformed cases
and manual/automatic state. Maintain it within the existing tracked system.

The user-facing report answers what finished, what remains, who handles it, the next
step and any specific owner decision. Follow
[the message rules](user-messages-and-responsibility.md).
No evidence dump or routine diary. Retain real amendments, approvals, consumption,
incidents and review evidence. Never self-certify independent host proof or create
recursive verification tasks.
