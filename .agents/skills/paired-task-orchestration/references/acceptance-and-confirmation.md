# Acceptance and definition confirmation

These are checks to perform, not assertions that a host installation or tests
already passed. Use actual source/plan/environment bindings and applicable safe
authorization. Do not run platform writes just to verify this skill's text.

## Outcome-based control

Normal programming within approved boundaries is the default. A primary delivers
the required outcome; its independent verifier assesses that outcome against
approved acceptance criteria and evidence. Do not require separate approval,
per-choice decision records, step-by-step narration, exhaustive method checklists,
or routine method-change ledgers for routine coding.

Selecting among unspecified equivalent methods is not itself a protected-plan
amendment. Exceptions, waivers, changed criteria/coverage, material changes to
scope/authority/execution/limits or safety/privacy/compatibility/data integrity/
ownership/recovery/completion, and changes to fixed requirements or protected
plans retain their applicable approval and amendment routes. Actual protected
payload changes retain full readback and affected-evidence renewal requirements.
Required approval, execution, incident, provenance, and acceptance evidence
remains mandatory; omitting a programming diary does not waive that evidence.

The tables below state required acceptance outcomes, not mandatory internal coding
methods or extra work-family gates. Optional examples do not add obligations.
Assess every applicable requirement; do not invent an assertion for every example.

## Definition-only confirmation

When installing this skill through project tasks, create the required dependent
definition confirmation using actual host interfaces and canonical companion
contracts where applicable. Scope SKILL.md-only corrections to that file; verify
references separately. Do not imply the hook or series was applied.

Compare the installed package against the authorized original specification:

- Valid frontmatter uses `paired-task-orchestration`, with a meaningful trigger
  description and a SKILL.md entry point below 500 lines.
- Single/multi-skill application is project-neutral: exact canonical targets and
  complete applicability are extracted; no mandatory router, Failure Gate, fixed
  task API, project backlog, stack or pair count.
- Installing a definition, implementing its app contract, independent verification
  and actual runtime readiness are separate outcomes. Full application requires
  actual app entry-point/state/configuration proof, not file presence alone.
- All target requirements have original fixed outcomes and evidence mappings;
  bundles retain independent per-target coverage, conflict handling and bindings.
- Standalone handoff includes finalization, canonical duplicate encoding, actual
  complete readbacks, original/resolved matrices and delivered-input readiness;
  actually governing router/companion constraints remain authoritative.
- Mandatory joint-batch companions use real alias/dependency resolution and full
  finalized readback before execution; no invented sequential history or guessed
  tool name. Required extra file/resource/application reviews are not collapsed.
- All required relative reference links resolve to canonical package files.
- Exactly one current implementation/verifier pair is the default drafting
  window; history/unrelated UI cards remain untouched.
- Full task payloads, genuine finalized primary readback before sequential verifier
  attachment (or verified joint commit/readback for an applicable required batch),
  exact dependencies, full verifier readback and real delivered-input readiness
  are required rather than title/status/metadata-only proof.
- Original specification/contracts are pinned; target/series/task IDs are real,
  namespace distinctions preserved, and no project is guessed.
- Actual duplicate lookup, stable keys, full payload reuse checks, partial pair
  recovery, and uncertain-write reconciliation precede retries.
- Verifiers audit first, list gaps, repair only explicitly approved scope, rebind
  changed evidence, renew validation, and obtain independent post-repair acceptance.
- Routine programming is delegated within approved boundaries; the verifier
  independently checks outcomes rather than each coding choice. Material
  exceptions and actual protected-plan amendments remain controlled.
- Source-only/bootstrap/runtime stages are distinguished without circular initial
  proof, hidden checks, or false operational readiness.
- User task approval remains separate; future drafting permission is conditional
  and scoped. No automatic test/activation/CI/recovery/disruption/merge/deploy grant.
- Required extra confirmation/verification tasks are not silently dropped to
  satisfy two cards; batching conflicts are surfaced before creation.
- Advancement requires actual current independent acceptance and successor
  delivery readiness. Genuinely unmet blocked/stale/failed tasks and
  administrative closure do not pass; expected negative/non-zero results are
  assessed against the declared criteria, not treated as automatic blockers.
- Every materialized primary/verifier plan preserves expected outcomes and their
  evidence requirements. Matching negative/non-zero results satisfy their
  criteria; they are not repair gaps or reasons to substitute zero/PASS.
- Tracked backlog/checkpoints and required repository deliverables are outside
  `.local/`, are not authorization registries, and do not claim clone-wide exclusion
  without shared host coordination. The `.local/` exception permits disposable
  submission copies only when the actual host requires the submission path.
  Complete authoritative tracked plans must exist outside `.local/` and be fully
  read back before a temporary copy is created; it must never be the only copy.
  Full copy comparison, independent persisted-plan/dependency/binding readback,
  and ordinary approval/readiness gates remain required. Initial drafting,
  authoritative deliverables, canonical sources, and runtime artifacts are excluded.
- Hook installation is optional, separately authorized, and begins with visible
  invocation-driven implementation/verification rather than a circular dependency.
- Automatic progression needs verified trigger AND actual wake-up/task-access/
  coordinator routes. Unsupported APIs, flags, local fixtures, and callback text
  cannot provide them.
- Manual resumption is available; polling is separately approved recurring work.
- Reports separate skill availability, definition/package delivery, real project
  installation, native task lifecycle, fixture outcomes, and enabled hook behavior.

List gaps before correction. Preserve unrelated canonical skills and the original
obligation baseline; material scope changes require applicable approval. Record
source readback separately from actual host acceptance.

## Host orchestration acceptance

Use safe authorized native host operations and retain actual refs/reports.
Instrumented fixtures can test logic but cannot prove real UI/task integration.

| Case | Required evidence |
|---|---|
| Single target | Complete canonical contract extraction; actual app wiring and each applicable requirement independently proved |
| Multiple targets | Each target retains original coverage/binding; shared checks do not hide a target gap |
| Framework not installed | A copied definition/README/orphan helper cannot satisfy implementation or runtime criteria |
| No router/Gate | Standalone supported pairing preserves handoff/readiness without imposing those unrelated frameworks |
| Required joint batch | Actual alias resolution, committed full records and dependency/readback before execution; no fabricated sequential history |
| First pair | Current complete proposed pair within the actual approved batching window, actual returned refs, genuine finalization under the applicable sequential/batch route, full readback |
| Existing pair | Resume reuses correctly bound tasks; no duplicate primary/verifier |
| Later backlog | Remaining pieces are durably recorded, not created as extra draft cards |
| Approval boundary | Neither task runs merely because created; verifier does not execute before delivered inputs |
| Shared instructions | Every materialized plan includes all applicable specification/shared safeguards |
| Routine programming | Equivalent unspecified methods need no new task, approval, choice ledger, or diary; the approved outcome and its evidence still pass independent review |
| Temporary submission copy | Actual host-required `.local/` submission path; complete authoritative tracked copy outside `.local/` preserved/read back first; complete copy comparison and independent persisted-plan/dependency/binding readback |
| Local-only drafting | `.local/` being the only writable location is not sufficient; no initial drafting or sole deliverable copy there; absent authoritative tracked copy blocks temporary-copy creation |
| Other deliverables | Submission-only exception does not permit `.local/` canonical skills, code, reports, checkpoints, durable evidence, final deliverables, or runtime artifacts |
| Material exception | Changed criteria/coverage, scope, authority, execution, limits, or protected safety/ownership/recovery/completion boundaries follow the applicable authorized route |
| Protected plan | Routine choices do not themselves amend a plan; actual fixed-requirement or protected-payload changes retain amendment, binding/readback, and evidence-renewal controls |
| Source stage | Only its declared source scope accepts; deferred runtime proof gates the runtime successor |
| Missing implementation | Verifier lists gaps, repairs within authority, invalidates old evidence, and gets independent final acceptance |
| Missing external authority | Blocked requirement and concrete next proposal; no synthetic grant or fake provider |
| Wrong/stale payload | Complete readback mismatch blocks creation-success/execution/advancement claims |
| Native Done without report | No advancement |
| Undelivered branch | No verifier/runtime successor launch using absent primary inputs; no automatic merge |
| Failed/blocked/stale/cancelled task | Unmet obligation remains current; a matching expected result does not itself make the task incomplete |
| Expected negative/non-zero result | Accept when the task's criteria expect or permit it, it is evidenced, and all other criteria pass; never use it to satisfy an unmet implementation requirement unless explicitly allowed |
| Outcome-contract readback | Primary and verifier plans retain declared expected results and evidence; no silent zero/PASS substitution or post-failure waiver |
| Expected rejection behavior | Verifier records it as satisfied, preserves raw evidence, and does not repair correct behavior merely to make the result zero |
| Finding task exposes later blocker | Finding task may complete against its own criteria; the genuine downstream prerequisite remains blocked |
| Owner direction | Administrative closure remains separate and cannot satisfy verification |
| Required third task | Conflict surfaced; no hidden obligation or dropped confirmation |
| Uncertain writes | Recover actual partial pair by trusted binding/request identity, not blind retry |
| Concurrent resume | Actual coordinator/idempotency establishes supported exclusion; absent capability is an explicit limitation/blocker |
| Last pair | No additional pair, auto-close policy, merge, deployment, or recurring work |
| Invocation fallback | Missing hook keeps bounded manual resumption functional and truthfully reported |

For automatic mode, also satisfy the complete live acceptance matrix in
[host-hook-contract.md](host-hook-contract.md). Do not label automatic mode
verified from this table, source review, or simulated events alone.

## Required report

Record request/specification baseline, canonical package/reference manifest,
project/task binding when applicable, exact scope/stage, actual checks performed,
raw outcomes/evidence, gaps before repair, amendments, independently accepted
post-repair snapshot, blocked/unperformed cases, responsible next actions, and
manual/automatic capability state.

Keep the report concise and requirement-linked. Retain actual amendments and
material exceptions, not a routine-method diary; preserve approval, execution,
incident, and provenance evidence needed to establish a valid outcome.

No recursive verification task creation or self-certified host proof.
