# Original scope and portable-definition acceptance

## User request

"Are you able to also write up a non-project specific Paired Task Orchestration skill? This way I can pair it with certain other skills to make sure the app installs their framework or contracts correctly."

## Authorized authoring outcome

Generalize the existing canonical paired-task-orchestration skill/package for any app and one or more explicit target skills. This is definition/resource authorship only. Do not initialize an app series, create native tasks, install a hook, execute frameworks, publish workspace instructions or alter a protected existing series. Preserve applicable existing safety and handoff behavior.

## Fixed checks

1. Identity stays paired-task-orchestration; main front matter/trigger is valid and SKILL.md stays below 500 lines.
2. The canonical package is self-contained for standalone pairing; every required relative module exists. An installed governing router is respected, but an unrelated missing router/Failure Gate is not imposed as a prerequisite.
3. The normatively required workflow contains no specific project identity, repository, existing task refs, fixed OS/database/stack/provider, hard-coded task function or universal staged series.
4. Single-skill application defaults to one implementation/dependent-verification pair; explicit multi-skill scope retains each target's full canonical applicability, bindings, conflicts and fixed acceptance coverage.
5. Definition/source installation is explicitly distinct from actual app framework/contract wiring, independent acceptance and actual runtime readiness. Readmes, orphan helpers, fixtures and native Done labels cannot substitute.
6. Complete original requirements, obligation/pre-install/delivered baselines, authentic approval boundaries, actual full finalized task readbacks/dependencies/delivery, stable duplicate bindings and unknown-write reconciliation remain mandatory.
7. Ordinary sequential creation preserves primary-finalization-before-attachment. A genuinely required companion batch uses actual supported alias/dependency/commit semantics and full finalized readback; conflicts/unknown interfaces are surfaced, not guessed.
8. Verifiers audit original outcomes independently, publish gaps before edits, repair only actually authorized scope, renew affected evidence and obtain fresh independent post-repair acceptance. Missing authority and real proof remain blocked.
9. Correct expected negative/nonzero findings are evaluated against original criteria; they cannot meet an unmet implementation requirement by relabeling a blocker.
10. Stage gates, source-versus-runtime evidence, real successor delivery and current independent acceptance govern advancement. No terminal-state rewrite, silent duplicate/retry/waiver, automatic merge/deploy or implied recurring work.
11. Tracked canonical plans/resources/reports remain outside .local. The original narrow host-required disposable submission-copy exception preserves all authoritative-copy/readback/permission conditions.
12. Optional automatic hooks remain separately authorized and verified; no hook is installed or enabled by this authoring or ordinary application workflow.
13. Routine programming needs no per-choice diary/approval; material safety/scope/criteria/coverage/authority/plan changes keep actual amendment and evidence-renewal requirements.
14. Full package installation/confirmation is not claimed from authorship. Any target-required file-only confirmation and resource/application verification remain distinct; no hidden follow-up is dropped to promise two cards.

## Correction boundaries

Later canonical SKILL.md-only confirmation may repair only that file under its actual governing scope. Reference-module/package review is separate if required. Full original criteria and actual delivered package must be accessible to reviewers; no criteria may be derived solely from installer output. No independent review or host-acceptance result is asserted by these checks.
