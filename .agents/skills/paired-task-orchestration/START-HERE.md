# Portable Paired Task Orchestration

This package provides instructions for creating and handing off implementation and
verification tasks. It is not an application, task scheduler or automatic approval.
It works with the project's actual supported task tools and canonical target skills.
No Failure Gate, Port Authority, router, framework or database is required.

## What a pair means

The implementation task finishes its assigned part.
The verification task checks that actual work, fixes authorized problems and records
the required separate final review. If the reviewer changes files, it does not approve
its own repairs. It uses a real authorized separate review context or host review.

The workflow retrieves that result and passes accepted files to later tasks.
You do not need to supply receipts, copy files or confirm the same review again.
A task starting or merging is not, by itself, proof that the review result arrived.

## What you decide

Choose the desired outcome and approve meaningful changes in scope, risk, cost,
access or permitted actions. The agent prepares technical settings and records.
Existing approval is reused when it actually covers the work.

Each task must state a finished result, not merely list missing inputs for you.
It continues everything safely permitted while resolving any remaining dependency.
It does not invent approval or claim success without evidence.

## Usage prompt

Use canonical Paired Task Orchestration to apply the selected canonical skill(s)
to the intended project. Discover the real task, delivery and review interfaces.
Prepare the smallest justified implementation/verification pair or preserve my
explicitly approved staged specification. Do not assume a fixed pair count.

Each task must finish its assigned result and handle its own technical preparation,
record retrieval, progress, evidence, allowed repairs and review coordination.
Assume I cannot supply original receipts. Retrieve existing approvals and review
results yourself. Ask only for a specific decision, permission or account action
that I must personally provide.

Preserve full original requirements, protected plans, actual dependencies, current
delivered files and separate post-repair review. Do not invent providers, reset
consumption, create duplicates or recursively create review tasks.

Explain what finished, what remains, who handles it and the next step in plain
English without assuming programming knowledge. Keep exact technical records.

Prepare drafts only unless execution is actually authorized. Automatic preparation
is optional separate work with real host support and approval. Without it, tell me
when to say "Prepare the next pair." That prepares drafts, not approves/runs them.

## Updating a definition

Canonical package: `.agents/skills/paired-task-orchestration/`.
Use only that canonical definition and its complete reference files.
Review differences before installation. Do not use `.local` as an authoritative
definition, drafting workspace or report store.
The narrowly defined temporary submission-copy exception remains intact.

This rewrite does not change existing project task plans, native statuses, approvals
or execution. Installing it does not silently amend protected plans already created.
SOURCE-MANIFEST.json and AUTHORING-CHECKS.md describe source/package checks.
Independent project acceptance and actual runtime tests are not claimed.
